## 目的・対象範囲

投稿時の手入力を減らし、無理のない範囲でSteam Web APIに任せる。外部リクエストとDBクエリをなるべく増やさない。

2026-10-08に実装作業の開始が依頼された。冒頭の項目の依存関係に従って進め、区切りのよい単位で検証結果と残件を報告する。実装完了後にユーザーがPR作成を依頼し、T7で両PRを作成。マージ・本番データ移行・デプロイは依頼されていない。

対象は管理者の新規・編集フォーム、情報取得API、画像表示、必要な保存経路の変更と検証。全ゲーム検索、全所有ゲームの実績巡回、定期同期、プレイ時間の履歴収集、複数Steamアカウントの連携は対象外。

## 決定事項・制約

| 項目                      | 方針                                                                                         |
| ------------------------- | -------------------------------------------------------------------------------------------- |
| ゲーム指定                | ストアURLまたはApp IDを入力。URLからの抽出はローカルで行う                                   |
| タイトル                  | Steamから自動補完し、手動修正可能にする                                                      |
| かかった時間              | **手入力を維持。自動補完・上書きしない**                                                     |
| 現在の総プレイ時間        | 初期実装では取得しない。タイトル・画像をGetItemsでまとめて取り、追加問い合わせを避ける       |
| コンプ日                  | 全実績解除と有効な解除日時を確認できる場合だけ最終解除日を候補にする。修正可能にする         |
| 評価3項目・放置ゲー・本文 | 手入力を維持                                                                                 |
| 詳細ページのストア表示    | 既存の公式ストアウィジェットを継続利用                                                       |
| 一覧画像                  | 固定CDNパスの組み立てを見直す。API経由または公式に案内された方法を優先し、方式を先に検証する |

「かかった時間」について、累計プレイ時間にはコンプ後のプレイが含まれるため、候補として自動補完する旧案は撤回済み。最終解除日時だけからコンプまでのプレイ時間は確定できない。履歴保存・定期取得による推定も今回の範囲外。

### T1の未決事項と判断条件

- 認証: 単一管理者のユーザー用Web APIキーとSteamID64をサーバーで扱う。環境変数名は `STEAM_WEB_API_KEY` と `STEAM_ID64`。キーの発行条件・失効時の扱い・公開設定の影響を確認し、非公開情報を取得できると仮定しない。現行のGoogle管理者認証を利用する。
- コンプ日: 実績が存在し、全件解除を確認でき、有効な解除日時が得られる場合のみ最終解除日を候補にする案。実績なし・未解除あり・日時欠落や0値の場合は手入力にする。返却一覧で全件判定できるか実データで検証する。日時から日付への変換は画面・保存・テストで整合させる。追加実績がある場合の限界を説明し、過去の初回コンプ日を保証しない。
- 画像: まず `GetOwnedGames` の応答で横長画像に使える情報を取得できるか確認する。`include_extended_appinfo` と `IStoreBrowseService/GetItems` は候補であり、公開利用条件・認証・返却形式を確認してから採否を決める。公式に案内されるアイコンと横長バナーを混同しない。
- 画像の代替案: 固定CDNパスの推測が必要なら改善済みとしない。公式ウィジェットは画像だけでなく価格・購入ボタンを含むため、一覧へ採用する場合はレイアウトと通信負荷を評価する。適切な方式を確認できなければ理由と候補の比較を残す。
- 問い合わせ予算: 基本2回、画像に別APIが必要な場合は最大1回追加する案を検証する。採用API・取得タイミング・画像参照の保存方式を確定してT2・T4へ引き継ぐ。制限回避のための別API巡回は行わない。

### T2の実装と検証（2026-10-08）

取得経路は `GET /api/v1/steam/post_details?appid=<App ID>`。返却値は `appId`、`title`、`imageUrl`、`completedAt`（ISO日時）、`warnings`。取得できない値はnullとし、項目別の案内を返す。所要時間は返さない。レスポンスはprivate/no-store。

### T3の実装と検証（2026-10-08）

`SteamPostImport` は入力時にAPIへ問い合わせず、取得ボタンでのみ取得する。フォーム内のApp ID別キャッシュを再利用し、再取得ボタンだけキャッシュを無視する。取得中は両ボタンを無効化し、入力変更・アンマウント時はAbortControllerと世代番号で古い応答を破棄する。ストアウィジェットも入力中の各桁では更新せず、取得が終わったゲームを表示する。

新規投稿の未編集タイトル・日付を補完する。既存投稿・手入力済み項目は保持し、候補ボタンを明示的に押した場合だけ上書きする。ゲーム指定変更時は未編集の補完値と候補をリセットし、手入力値は残す。所要時間・評価・本文は補完処理から変更しない。日付はISO日時をDateへ変換して既存DatePickerに渡す。

ストアURLはHTTPS・ `store.steampowered.com/app/<id>` のみ解釈し、保存ペイロードには数値App IDを渡す。画像URLは取得APIが返すが、この段階では保存ペイロード・DB・一覧へ渡していない。T4でPrismaスキーマと保存型の拡張を行う必要がある。APIから値を取得できない場合も手動編集を継続できる。
